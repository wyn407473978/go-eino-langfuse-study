## 2. 时间与学习方法

暂按每天 2 小时、每周 5 天安排：核心路线 8 周、40 次学习，共约 80 小时；运维扩展再安排 1–2 周。每天只有 1 小时时，可以将一次任务拆成两次，总周期相应延长。

- 自己实现从环境读取 API Key、创建 ChatModel、组织消息、调用 Generate、输出回答；模型名和基础地址按你的偏好直接写在代码配置中。
- 先只用命令行入口，不加入 Gin 和 Langfuse。
- 验收：更换问题可以得到回答；缺少必要配置时能明确失败；日志不输出密钥。
- 思考：接口地址、模型名称、API Key 各自配置错误，会在哪一步出现问题？

### D03：消息历史、超时与错误

- 用明确的消息列表完成两轮对话，观察第二轮是否能使用第一轮信息。
- 为模型调用设置超时，识别超时与认证错误。
- 人为设置很短的超时，观察程序行为，再恢复正常配置。
- 验收：能解释“模型记得上一轮”依赖什么；请求失败时不继续读取无效响应。

### D04：接入熟悉的 Gin

- 新增 POST /chat：接收 message、user_id、session_id，返回回答或清晰的错误。
- 先保持无历史，只完成 HTTP → 业务调用 → ChatModel 的过程。
- 使用请求 context，并处理空输入、字段不合法、模型失败。
- 验收：正常请求、无效请求、模型超时三种结果可区分；能说清请求取消如何传给模型。

### D05：内存会话与周验收

- 加入有限长度的内存历史，按用户与会话共同隔离；考虑并发访问。
- 明确历史截断策略、失败的回答是否入历史、进程重启后会发生什么。
- 用两个不同用户、多个会话交叉验证，不能串历史。
- 验收：不看完整示例，讲清接口到模型的调用过程；演示两轮对话、会话隔离、错误处理。
- 复盘问题：把 Gin handler 中的模型调用换掉，需要改动哪些位置？目前有必要引入数据库吗？

## 6. 第 2 周：第一条追踪与正确的父子关系

目标：将自己写出的应用接入 Langfuse，能读懂并排查追踪数据。

阅读范围：[Eino 回调包](https://pkg.go.dev/github.com/cloudwego/eino-ext/callbacks/langfuse/v2)、[Langfuse OTel 接入](https://langfuse.com/integrations/native/opentelemetry)、[良好追踪的标准](https://langfuse.com/docs/observability/best-practices)。

### D06：准备 Langfuse 项目并跑通 CLI 追踪

### D07：把追踪接入 HTTP 请求

- 每次 /chat 调用创建独立的请求追踪，返回可定位此次请求的 trace_id。

- 正常和异常路径都结束追踪；关闭时使用有界、仍可用的关闭 context。
- 验收：三次 HTTP 请求对应三条追踪；错误调用不会一直显示为未结束。

### D08：用户、会话和环境属性

- 设置 user、session、tags、environment；有 Git 版本时再加入 release，否则先用明确的开发版本标记。
- 在 UI 验证根节点和模型子节点都能使用预期字段过滤。
- 比较普通 OTel 属性和 Langfuse metadata 映射，不只看代码有没有设置。
- 验收：同一会话的多次请求能聚合；按用户、标签和一个自定义字段找到目标观测。

### D09：手动补一个业务 span

- 理解 TracerProvider、Tracer、Span 和 context 的关系。
- 给加载历史消息增加手动 span，保证与回调使用兼容的 Provider 和同一请求上下文。
- 先画预期树，再对照实际树。
- 验收：历史加载与模型调用按真实执行关系出现在同一追踪中，没有重复根节点。

### D10：做三组故障对照

- 分别观察错误密钥、错误 context、未等待导出就退出时的行为。
- 每次只改变一个条件，记录现象、日志和修复方法。
- 不要求每次漏掉 Shutdown 都必然丢数据；要解释批处理时机为什么会影响结果。
- 验收：用自己的话解释 trace、observation、generation、session；能从证据区分业务失败与上报失败。

## 7. 第 3 周：流式、成本和工具调用

目标：能观察响应过程，并理解模型为什么、怎样调用工具。

阅读范围：Eino 用户手册中的流式编程、ChatModelAgent、Tool 和 Runner 小节；Langfuse 的 token、成本与观测类型文档。ADK 只读当前用到的部分。

- 记录完整输出；检查供应商是否返回 usage，不把缺失用量当成零用量。

### D12：通过 Gin 输出 SSE

### D13：比较延迟、token 与成本

- 区分端到端耗时、首个有效输出到达耗时和模型生成耗时，记录测量位置。

- 创建错误请求、慢请求、高成本请求三个筛选视图；名称以当前 UI 为准。
- 验收：能定位一条慢请求的主要耗时；说明成本为 0 或 usage 缺失可能有哪些原因。

### D14：先做一个可直接调用的工具

- 自己定义“查询办事进度”工具的名称、说明、参数结构和返回结构。
- 先直接验证工具，再交给 Agent；未知业务编号返回可区分的结果。
- 使用模拟数据，不接真实业务系统。
- 验收：正常参数、非法参数、编号不存在三种情况行为明确。

### D15：Agent 选择两个工具

- 新增“查询活动”工具，接入 ChatModelAgent 和 Runner，限制最大执行步骤。
- 验证闲聊不调工具、进度问题选进度工具、活动问题选活动工具。
- 故意让工具失败一次，检查 Agent 行为、错误和工具参数在追踪中是否可解释。
- 验收：展示一次工具成功和一次失败的完整过程；说明 Agent 与一次普通 ChatModel 调用的区别。

## 8. 第 4 周：Prompt 管理与用户反馈

目标：不重启应用即可切换 Prompt，并能把用户反馈关联回请求。

阅读范围：Langfuse Prompt 管理、缓存、Prompt 关联，以及评分文档；进入任务时核对当前 REST 规范。

### D16：写最小的 REST 客户端

- 从“按名称和 label 获取一个 text Prompt”开始，只封装当前需要的能力。
- 处理认证、超时、非成功状态、解码失败与资源关闭。
- 客户端配置外置；区分传输错误与业务资源不存在。
- 验收：正常获取、错误认证、名称不存在、超时四种结果可解释。

### D17：编译变量并关联版本

- 先支持简单文本变量；明确缺变量、额外变量和重复变量的行为。
- 将实际使用的 Prompt 名称与版本关联到对应 generation，核对当前属性规范。
- 使用本地假响应验证变量边界，避免每个小测试都调用付费模型。
- 验收：UI 中能从 generation 找到实际 Prompt 版本；缺变量不会悄悄形成错误提示词。

### D18：加入缓存和兜底

- 先做简单 TTL 缓存，再明确并发访问、过期刷新、旧缓存和内置默认版本的策略。

### D19：版本切换与 chat Prompt

- 创建两个 Prompt 版本，切换 production label，在预设缓存窗口后观察效果。
- 再支持当前应用需要的 chat Prompt 与历史消息占位；Prompt 引用递归解析留作扩展。
- 在 Playground 手工比较相同输入，记录配置差异。
- 验收：无需重启即可切换版本；能指出新请求实际使用了哪个版本和哪些消息。

### D20：最小用户反馈

- 建立评分定义，新增 POST /feedback，支持一种明确的点赞/点踩评分。

- 收集第一批正常、错误、低质量案例，不强行在一天凑满标注量。
- 验收：一条请求可以看到用户反馈；非法值不写入；明确正式系统还需增加归属校验和访问控制。

## 9. 第 5 周：RAG 与人工质量标准

目标：理解检索和生成的边界，建立后续自动评估的依据。

阅读范围：Eino 文档中的 Document、Embedding、Retriever 和 RAG 相关示例。选一个支持所需能力的 embedding 适配器，记录版本与维度。

### D21：准备小型知识库与标注标准

- 逐步准备约 20 篇短文档，内容涵盖材料、时限、活动等，保留文档 ID 和来源。
- 写出约 10 个可回答问题和 5 个库中无法回答的问题，并标明依据。
- 定义人工判定标准：答对、部分正确、无依据、应拒答；说明边界案例。
- 验收：别人能根据同一份标准复核你的判断，而不是只凭回答是否“流畅”。

### D22：切分、向量化与缓存

- 先实现简单可解释的切分，保留 chunk_id、document_id 和来源。
- 对文档向量化并保存可复用的本地结果，记录模型与维度，避免重复花费。
- 验收：能从一个向量结果反查原文；能解释切分过大和过小各自的问题。

### D23：先单独验证检索

- 用内存向量实现或接入检索，明确相似度算法和 top-k。
- 暂不调用生成模型，逐条查看问题命中了哪些 chunk。
- 对没有相关内容的情况制定策略；阈值需通过样本观察，不随意照搬固定数字。
- 验收：展示若干命中与未命中案例，并解释排序依据；知道 embedding 和检索不等于生成答案。

### D24：组合 RAG 并观察各步骤

- 把问题、检索上下文和回答约束组合起来，要求回答引用来源或表达证据不足。
- 观察 query embedding、retrieval、generation 的耗时和输入输出。
- 控制上报内容大小，保留文档标识与必要片段，不把整个知识库塞进 span。
- 验收：能沿一条追踪定位“检索错”或“生成没有遵循上下文”。

### D25：人工复核与差评队列

- 在功能可用时建立差评复核队列，并由你实现必要的自动入队调用。
- 累计复核约 20 个案例；没有队列权限时先用本地表记录，标明待补平台操作。
- 区分用户反馈和人工评审，保留理由和标准版本。
- 验收：输出至少三类错误及案例：检索失败、回答无依据、工具或路由问题。

## 10. 第 6 周：Graph 和第一轮离线实验

目标：做出明确的意图路由，并通过固定样本比较两个版本。

阅读范围：[Chain/Graph 编排介绍](https://www.cloudwego.io/zh/docs/eino/core_modules/chain_and_graph_orchestration/chain_graph_introduction/)、Langfuse 数据集和[OTel 实验规范](https://langfuse.com/integrations/native/opentelemetry/experiments)。

### D26：确定意图结构和数据集

## 11. 第 7 周：自动评估、校准和 CI

目标：让“质量有没有变好”有可复查的证据。

阅读范围：[评估概览](https://langfuse.com/docs/evaluation/overview)、LLM-as-a-Judge、评分分析、Code Evaluators 和 CI 文档。以下质量阈值是练习目标，最终由基线结果和业务需要决定。

### D31：扩展问答数据集

- 整理约 20 条 RAG QA 样本，包含参考答案、支持文档、应拒答样本和已发现的失败案例。
- 明确检索正确、答案正确、依据充分分别怎样判断。
- 固定样本版本并保留部分验证样本，不因一次实验不理想就删除困难题。
- 验收：数据能稳定复用；知道参考答案文字不同不一定代表回答错误。

### D32：只启用一个在线裁判

- 从“答案是否被检索内容支持”开始，定义评分范围和判定说明。
- 在开启规则前确认 observation 中具有问题、上下文和答案等必要变量。
- 先用几个指定案例验证映射，再对满足条件的观测进行采样。
- 验收：能解释一次分数及理由；不把规则没触发、映射缺失和裁判判低分混为一谈。

### D33：用人工标注校准裁判

- 复用第 5 周的标注案例，比较人工和裁判判断。
- 统计一致率与具体分歧；保留独立案例检查修改是否只适配了熟悉样本。
- 确定性约束继续用 Go 检查；如要练平台托管 Code Evaluator，再按支持环境写小型 TS/Python 脚本，脚本仍由你写。
- 验收：列出典型误判并解释改进；不把 LLM 裁判当作绝对真值。

### D34：评估采样与成本

- 记录业务调用与评估调用的次数、成本和规则过滤条件。
- 先在少量样本上全量验证，再打开例如 20% 的采样，观察符合条件的请求集合。
- 验收：能解释为何 50 个符合条件的请求不保证恰好产生 10 次评分；能排查缺分原因并给出评估预算。

### D35：质量门禁

- 将 runner 接入 CI，明确数据集版本、配置、凭据来源和退出行为。
- 先对明确可判定的意图任务设门槛，例如在基线支持时采用 90% 的绝对准确率并限制相对退化。
- 故意引入一个明显退化版本，验证门禁失败；恢复后验证通过。
- 外部服务不可用单独报告为运行失败，不声称是模型质量退化；CI 不假通过。
- 验收：保留一次通过和一次失败的证据，并能定位造成退化的样本。

## 12. 第 8 周：监控、故障处理与综合验收

目标：应用不仅能跑，还能解释故障、控制上报开销并完成恢复。

阅读范围：当前 Metrics API、Dashboard、Monitors、回调采样与关闭配置，以及 OTel 上下文传播。功能是否可用以实际部署和授权为准。

### D36：建立最小健康看板

- 关注请求量、延迟、错误率、成本和反馈质量，先定义每个指标的统计对象。
- 用 UI 看板和一个 Go 指标查询练习，固定时间范围、时区与过滤条件。
- 验收：抽查少量原始记录可解释聚合结果；不会混淆请求量与 generation 数。
- P95 只作为练习指标；样本太少时明确标记，不能据此声称生产性能达标。

### D37：告警接收

- 支持 Monitors 时配置一个可控阈值，由你编写最小 Webhook 接收端。
- 先用测试事件验证接收，再制造真实符合规则的错误。
- 验证来源校验、重复事件和接收失败的处理策略；没有平台告警权限时标记待补，不宣称完成同等功能。
- 验收：有事件触发、接收时间和关联请求的证据；实际第三方机器人通知可留作后续选做。

### D38：脱敏、截断和采样

- 用合成手机号等测试数据验证脱敏，覆盖 Prompt、模型输入输出、工具参数、metadata 和错误日志。
- 对单字段和整体载荷设合理上限；保留被截断的提示和可追查 ID。
- 验证采样策略，不只配置一个数字；检查是否破坏父子关系。
- 验收：UI 与日志找不到约定禁止出现的原始测试字段；大输入不会造成无界上报。

### D39：Langfuse 不可用与优雅关闭

- 在独立学习环境断开 Langfuse 连接，分别验证已有 Prompt 缓存、无缓存启动、观测队列积压。
- 用受控的小规模请求比较成功率、延迟和内存；昂贵模型调用不做无预算压测，可用假模型隔离业务验证。
- 明确上报丢弃、重试和导出超时行为，发送终止信号验证有界关闭。
- 验收：说明业务是否仍可用、退化窗口和数据丢失边界；不承诺任何故障下都完全没有额外开销。

### D40：综合演示与薄弱点复盘

- 演示闲聊、知识问答、工具成功、工具失败、证据不足、用户反馈六类请求。
- 演示一次不重启的 Prompt 切换、两版实验对比、一次 CI 拦截，以及上报服务故障。
- 独立解释一条请求的执行路径、Prompt 版本、耗时、成本与质量评价。
- 产出：演示记录、当前限制、待修复问题和下一步选择。
- 验收：关键任务既有运行证据又能解释原理；未完成项保留在清单里，不能用“功能写过了”代替验收。

## 14. 每周通过的统一标准

每项任务同时检查三件事：

1. 能运行：有正常路径和至少一个关键异常路径的结果。
2. 能解释：说明输入输出、调用关系和主要取舍。
3. 能排查：给出故障现象、定位证据和修复方法。

重要逻辑使用有价值的验证：会话隔离与并发、Prompt 缓存过期和兜底、评分关联、路由无效输出、实验统计和关闭行为。不要为每个简单字段封装编写重复实现的测试，也不要只依赖模型回答“看起来正确”。

每周复盘只回答四个问题：我现在能独立做什么？哪一个概念仍解释不清？哪一个故障是靠证据定位的？下一周开始前还缺哪个前置条件？

如果关键验收不过，下一次先修复或补练，不为了赶周数继续叠加功能。
